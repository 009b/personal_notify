# Архитектура: personal_notify

## Общая схема

Два входа в приложение, общие сервисы:

```
┌──────────────┐         ┌──────────────────────────┐
│ системный    │  cron   │  CLI-задача (bot.tasks)   │
│ cron         ├────────▶│  короткоживущий процесс   │
└──────────────┘         └────────────┬─────────────┘
                                       │
┌──────────────┐  polling ┌───────────▼─────────────┐
│ Telegram API ├─────────▶│  bot (aiogram, демон)    │
└──────────────┘          │  handlers, приём событий │
                          └────────────┬─────────────┘
                                       │
                          ┌────────────▼─────────────┐
                          │         services         │
                          │  llm · weather · notifier │
                          └────────────┬─────────────┘
                                       │
                          ┌────────────▼─────────────┐
                          │  storage (интерфейс)     │
                          │  дефолт: SQLite (stdlib) │
                          └──────────────────────────┘
```

- **bot (демон)** — долгоживущий aiogram-процесс под systemd: команды и приём событий.
- **CLI-задача** (`bot.tasks`) — короткоживущий процесс, запускаемый из cron: формирует и отправляет оповещение по расписанию, затем завершается. Расписание живёт в crontab, не в коде.

## LLM / Ollama

- Ollama локальная: `127.0.0.1:11434`.
- Обвязка-сервис (`OllamaClient.process_text`) вызывает модель (`POST /api/chat`) для обработки текста.
- Выбор модели и опции — из конфига (дефолтная модель + override на вызов).
- Применение: обработка текста оповещений (первое — погода). Если LLM недоступна, задача `weather` отправляет шаблонный текст (без HTML).
- Задача `weather` вызывает LLM с `think=False` (рассуждения для оформления не нужны; ускоряет ответ примерно вчетверо: ~15–20 с против ~60–73 с). Флаг `think` опционален и общим клиентом по умолчанию не передаётся.
- Холодный старт модели может занимать > 60 с, поэтому `request_timeout` по умолчанию 180 с.

### Разметка Telegram
- Оформленный LLM текст отправляется с `parse_mode=HTML`.
- Telegram поддерживает лишь ограниченный набор тегов, а вывод модели может содержать неподдерживаемые (`<br>`, `<p>` и т.п.). Поэтому перед отправкой текст пропускается через `bot/services/telegram_html.py` (`sanitize`): `<br>` → перевод строки, неразрешённые теги удаляются, атрибуты сбрасываются, «голые» `<`, `>`, `&` экранируются, подряд идущие переводы строк схлопываются в один (одинарные отступы).

## Погода (Gismeteo)

- Источник — открытый JSON-эндпоинт `https://www.gismeteo.ru/api/v2/weather/forecast/<city_id>/` (без токена, тот же поток, что виден на странице города). Москва = `city_id` 4368.
- Ответ — список точек: `kind="Obs"` (текущее наблюдение) и `kind="Frc"` (прогноз) с `tod` (часть суток): 0 — ночь, 1 — утро, 2 — день, 3 — вечер.
- `Forecast` содержит: температуру по всем частям суток ближайшего дня (`parts_of_day` — ключи `night`/`morning`/`day`/`evening`, округлённую до целых), описание из `cloudiness.scale_3`, ветер, влажность, осадки. Текущая температура и давление не используются.
- Формат сообщения компактный, только на русском, с объединением по смыслу: заголовок «Погода в <city>» (city задаётся в конфиге в нужном падеже, напр. «Москве»); строка «описание + ветер + порывы»; температура по частям суток одной строкой; строка «осадки + влажность».
- Беззвучная доставка: `weather.silent` в конфиге → `disable_notification` при отправке (сообщение приходит без звука).

## Новостной дайджест

- Отдельная cron-задача `news` (batch-пайплайн), не потоковый `EventProcessor`.
- Чтение каналов — `bot/services/telegram_reader.py` через Telethon (MTProto-юзербот). Нужны `TG_API_ID`/`TG_API_HASH` (.env) и session-файл (`TG_SESSION_PATH`, по умолчанию `data/userbot.session`). Сессия создаётся один раз интерактивно: `python -m bot.tasks news_login`.
- Пайплайн `bot/services/news/pipeline.py`: `collect` (за окно `window_hours`) → `filter_posts` (LLM по `exclude_topics`, отсев детерминированно по индексам) → `summarize` (LLM группирует по темам, ссылается на источники как `[N]`) → `format` (подстановка `[N]` → HTML-ссылка из `Post.url`, sanitize).
- Ссылки на исходные посты подставляет код, не модель (чтобы не искажать URL).
- Пустой результат → «За последние сутки новостей нет».
- Конфиг — секция `news` (`sources`, `window_hours`, `exclude_topics`, `max_posts`, `max_post_chars`, `silent`); промпты `ollama.prompts.news_filter` / `news_digest`.
- Беззвучная доставка: `news.silent`.

## Хранилище данных

- Доступ через общий интерфейс `Storage` (`is_seen` / `mark_seen` / `close`) — точку хранения легко сменить.
- Дефолтная реализация `SqliteStorage` на stdlib `sqlite3` (без внешних зависимостей); фабрика `build_storage` выбирает бэкенд по конфигу.
- Назначение: дедупликация событий (какие уже обработаны). Путь `:memory:` — временная БД (тесты).

## События

- `EventSource.poll()` — асинхронный поток нормализованных `Event(key, text)`.
- `EventProcessor` пропускает уже виденные события (через `Storage`), новые отправляет (через `Notifier`) и отмечает обработанными.
- Конкретные источники и способ приёма (webhook / polling) — открытый вопрос (см. SPEC §8).

## Зависимости

- Используются: `aiogram` (Telegram), `python-dotenv` (`.env`), `httpx` (Ollama, Gismeteo), `PyYAML` (конфиг).
- `sqlite3` — stdlib.
- Не используются: сторонние планировщики (вместо них системный cron).

## Деплой

- Демон бота — systemd-сервис: `deploy/personal-notify.service` (ExecStart `python -m bot.main`, `EnvironmentFile=.env`, `Restart=on-failure`).
- Оповещения по расписанию — crontab: `deploy/crontab.example` (`CRON_TZ=Europe/Moscow`, `0 8 * * *` → `python -m bot.tasks weather`, лог в `logs/weather.log`).
- Установка описана в README.
